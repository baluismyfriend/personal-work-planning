ADDENDUM 3 - SAFARI AUTO BACKUP FIX
------------------------------------------------------------
Reported issue: clicking "Enable Auto Backup" in Safari showed
"Automatic file backup requires Microsoft Edge or Google Chrome
with File System Access support." and did nothing further.

Root cause (verified via current documentation, not assumed):
Safari (WebKit) and Firefox do not implement window.showSaveFilePicker
or the rest of the File System Access picker API that lets a web
page get a handle to a user-chosen file on disk - this is a platform
limitation of those browser engines, confirmed still true as of
2026, not a bug in this app's code. A page cannot add a missing
browser API to itself, so simply "fixing the code" to call
showSaveFilePicker in Safari cannot work - the function does not
exist there. Two possible workarounds were evaluated and rejected
before choosing the implemented fix:
  - Origin Private File System (OPFS) via FileSystemFileHandle.
    createWritable(): still Chromium-only in practice; Safari only
    supports the synchronous OPFS handle, and only inside a
    dedicated Web Worker.
  - Loading a separate worker.js file to use that synchronous OPFS
    handle: rejected because this app is required to run by simply
    double-clicking index.html with no server (file:// origin), and
    browsers reliably refuse to load an external Worker script from
    a file:// page, which would silently break the feature in every
    browser, not just Safari.

Implemented fix: script.js now has two real, working Auto Backup
tiers, chosen automatically based on what the current browser
actually supports:
  - Tier 1 (Chrome/Edge/Opera): unchanged - the original File
    System Access picker flow, writing to a real user-chosen file
    on disk.
  - Tier 2 (Safari/Firefox/any browser without the picker API, as
    long as IndexedDB exists - true in effectively all modern
    browsers, including Safari, even under file://): a genuinely
    automatic backup that silently keeps a full workbook snapshot
    in the browser's IndexedDB storage after every change (same
    250ms debounce and overlapping-write protection as Tier 1), with
    no picker dialog and no repeated re-authorization after a
    restart. A second click, once enabled, downloads a real portable
    .json copy of that snapshot on demand.
  - Only if IndexedDB itself is entirely unavailable (extremely
    rare) does the button now show an alert, and its wording was
    corrected to no longer claim Edge/Chrome are the only option:
    "Automatic backup requires a browser with local storage
    (IndexedDB) support, which is not available here."

Re-run after this fix:
- node --check script.js -> PASS, no syntax errors.
- grep confirms the old function name supportsAutoBackup no longer
  exists anywhere (cleanly renamed/split into supportsFsaAutoBackup
  and supportsIdb) and there are no duplicate function definitions

  handleAutoBackupButton, queueAutoBackupWrite, writeAutoBackupNow,
  writeSnapshotBackupNow, setAutoBackupButtonState, idbSaveSnapshot,

ADDENDUM 5 - ROUGH NOTES / IMPORTANT TIMELINES CHANGES NOT
APPEARING (ROOT CAUSE + FIX)
------------------------------------------------------------
Reported issue: after Addendum 4, the new Rough Notes columns
(Date, Task/Event) and the new Important TimeLines columns (S#,
Type, Priority, Topic/event, Deadline date) were not visible when
reopening the app.

Root cause: this app deliberately loads from localStorage first and
only falls back to the built-in default workbook when nothing is
saved yet (see README section 2 / SECURITY_TESTS check 14 -
localStorage is the primary persistence layer, by design). Anyone
who had already opened an earlier version of this app has an old
workbook - with the old Important TimeLines columns
(Payer/DEV/SIT/UAT/PROD) and the old single-column Rough Notes
(Notes only) - already saved in their browser's localStorage under
workPlanningFinal.v2.data. Loading the new index.html/script.js
files does not touch that already-saved browser data by itself, so
the OLD column layout kept loading every time, even though the new
default workbook (used only for brand-new, empty browsers) was
correct. This is the same category of issue the app already solved
once before for the "Completed tasks" page (see the original
NORMALIZATION AND INPUT SECURITY spec item: "If old valid saved data
does not include Completed tasks, append that required page
automatically and normalize it") - it simply had not yet been
extended to cover these two newly-changed pages.

Fix implemented: normalizeWorkbook() (the same function that already
runs on every app load, on every import, and immediately after
startup normalization is saved back to localStorage) now also
detects and migrates these two specific pages:
  - Important TimeLines: if the sheet's columns are not already
    exactly ["S#", "Type", "Priority", "Topic/event",
    "Deadline date"], every existing row is converted to the new
    schema. Rather than silently discarding old Payer/DEV/SIT/UAT/
    PROD values, each non-blank old value is preserved as a
    readable "ColumnName: value" fragment inside the new
    Topic/event column (e.g. "Payer: gg; DEV: 02/02/2029; SIT:
    02/13/2029"), so no prior data is lost - it is just no longer
    split across the old columns.
  - Rough Notes: if the sheet's columns are not already exactly
    ["Date", "Task/Event", "Notes"], every existing row's Notes
    text is preserved, and the two new columns are simply added
    blank alongside it.
  - Brand-new sheets that already match the new schema (including
    ones a user has started editing since this fix) pass straight
    through unchanged - the migration only rewrites sheets that are
    still on the old layout, and is safe to run on every load
    (idempotent).

ADDENDUM 6 - NEWLINE RETENTION FIX, COMPLETED TASKS REORDER, AND
PWA (ADD TO HOME SCREEN) SUPPORT
------------------------------------------------------------
Three changes in this round:

1. NEWLINE RETENTION FIX. Root cause confirmed by direct testing:
   document.execCommand("insertText", false, "\n") - previously used
   for both the Enter key and paste - can be normalized by the
   browser's contenteditable implementation into a <br> element
   rather than a literal newline text node. A <br> element still
   displays as a visual line break while editing, but contributes
   NOTHING to a plain .textContent read, so the line break silently
   disappeared the moment the cell's save-on-blur handler read
   div.textContent. Fix: (a) a new insertTextAtCursor() helper
   manually inserts a genuine text node via the Selection/Range API
   instead of execCommand, for both Enter and paste, so the newline
   is guaranteed to be literal text from the start; (b) a new
   extractPlainText() helper replaces the raw .textContent read on
   blur, walking the actual DOM and explicitly converting any <br>
   or block-element boundary it finds into "\n" - a defense-in-depth
   safety net in case any other browser quirk (autocorrect,
   drag-and-drop, etc.) still produces a stray <br>. sanitizeCell()
   was also updated to normalize \r\n/\r into a single \n, so pasted
   Windows-style line endings are stored consistently.

2. COMPLETED TASKS MOVED TO LAST. buildDefaultWorkbook() now builds
   pages in the order Daily planning -> Week planning -> All future
   Tasks -> Important TimeLines -> Road Map - Pending -> Rough Notes
   -> Completed tasks, for brand-new installs. For existing saved
   workbooks (which may have Completed tasks anywhere, including its
   old 4th position), normalizeWorkbook() now unconditionally moves
   whichever sheet is named "Completed tasks" to the end of the
   array on every load - this runs immediately after the existing
   "ensure Completed tasks exists" step and is idempotent (a
   workbook where it's already last is left untouched). Because
   reordering pages changes what a stored numeric page index points
   at, a new loadPreviouslySelectedSheetName() helper independently
   re-reads the raw saved workbook/index pair to recover which page
   the user had open by NAME (not just index) before normalization
   changed the order, so a returning user lands back on the same
   page they left, not whatever page now happens to sit at their old
   numeric index. This does not change the exact storage KEYS
   (workPlanningFinal.v2.data / .selectedSheet remain as specified)
   - only how the already-specified selectedSheet index is resolved
   at load time.

3. PWA / "ADD TO HOME SCREEN" SUPPORT. Four new files were added:
   manifest.json, apple-touch-icon.png (180x180), icon-192.png, and
   icon-512.png (the icons reuse the existing teal brand gradient
   and "PWP" mark already used for the in-app header logo, generated
   programmatically - no external image assets were fetched or
   embedded). index.html gained a <link rel="manifest">, a
   <link rel="apple-touch-icon">/<link rel="icon">, and standard
   theme-color / apple-mobile-web-app-* <meta> tags so that visiting
   the hosted page in Safari on iPhone and choosing "Add to Home
   Screen" installs a real, standalone, full-screen app icon. style
   .css gained env(safe-area-inset-top)/env(safe-area-inset-bottom)
   padding on the header and floating Add Row button so they clear
   the iPhone notch/home-indicator when running full-screen. None of
   this introduces a server, a network call, or a build step -
   these are purely local, static files; they only take effect once
   the existing three app files (plus these four) are hosted at a
   real address by the user (documented in README section 15),
   because iOS does not allow installing a page opened via a local
   file:// path, regardless of what a manifest declares.

ADDENDUM 7 - MOBILE-FRIENDLY LAYOUT (PHONE-WIDTH REDESIGN)
------------------------------------------------------------
Reported issue: pages did not display properly on iPhone - the
fixed-width, many-column table layout (designed for a desktop
screen) did not fit a phone's narrow viewport.

Change scope: this was a CSS/markup adjustment, not a change to any
data-handling, storage, import/export, or auto-backup logic.

1. COMPACT HEADER ON PHONE. A new @media (max-width:680px) block
   shrinks the brand icon, page title, and top action buttons, and
   hides the header subtitle text, so the header takes up
   meaningfully less vertical space on a phone screen while staying
   fully legible - addressing "keep the heading also small."

2. TABLE COLLAPSES INTO READABLE STACKED CARDS. At that same
   breakpoint, the wide, fixed-column data table (previously
   requiring horizontal scrolling and tiny per-column text on a
   phone) switches to a standard responsive-table pattern: the
   column-header/filter row is hidden, and each table row becomes
   its own rounded card with every field stacked vertically, each
   preceded by a small uppercase label naming its column (e.g.
   "Task/Meeting", "Due date", "Status"). Every existing field type -
   the editable text cells, the colored Status dropdown, the
   calendar-picker Due date/Deadline date control, and the Copy/
   Move/Delete action buttons - renders inside these cards exactly
   as before, just stacked rather than packed into narrow columns.
   This directly addresses "task details must be visible" and
   "allow clearly to enter new task details": every field is full-
   width, legible, and has a much larger tap target than the
   original dense grid would allow at phone width.
   Implementation note: buildRowElement() now sets a data-label
   attribute (equal to the column name) on every <td> it builds, on
   every page; the CSS reads that attribute via `content:attr(
   data-label)` to render the per-field label. This required a
   one-line change to add the attribute, with no change to what
   data is stored or how it's read/written.
   Trade-off, stated plainly: column sorting and the per-column
   text/value filters are hidden at this breakpoint, since they
   depend on the column-header row this layout removes. They remain
   fully available exactly as before on tablet/desktop widths
   (>680px). This was a deliberate simplification to prioritize
   "task details visible" and "easy entry" on a phone screen over
   preserving every desktop control in a cramped space; nothing was
   removed from wider screens.

3. SWIPE LEFT/RIGHT TO CHANGE PAGES. A new touchstart/touchend
   listener pair on the main content area detects a horizontal
   swipe gesture (minimum 70px of horizontal movement, and the
   horizontal movement must clearly dominate any vertical movement)
   and moves to the next/previous page accordingly, mirroring what
   tapping a nav pill already does (same goToSheetIndex() function,
   also now shared by the nav-pill click handler). A swipe that
   starts inside an editable cell, an input, a select, a button, a
   resize handle, or a link is ignored, so it can never hijack text
   selection, typing, tapping a button, or dragging a column
   resize-handle. Both listeners are registered with {passive:true}
   and never call preventDefault(), so normal vertical scrolling of
   the page is completely unaffected.
